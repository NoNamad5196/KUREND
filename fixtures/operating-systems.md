# 운영체제 4장 프로세스 스케줄링

이 노트는 한 학기 운영체제 수업에서 CPU 스케줄링을 설명하기 위한 자체 작성 자료다. 별도 표시가 없으면 CPU는 하나이고, 문맥 교환 비용은 0이며, 준비 상태의 프로세스만 선택 후보라고 가정한다. 실제 시스템은 코어 수와 장치 특성이 다양하므로 예제의 결론을 그대로 일반화하지 않는다. 알고리즘 이름을 외우기보다 어떤 정보를 이용해 누구에게 CPU를 주는지 설명하는 데 초점을 둔다.

## 1. 스케줄링의 출발점

CPU 스케줄링은 준비 큐에 있는 프로세스 중 다음에 CPU를 사용할 프로세스를 선택하는 일이다. 프로세스가 디스크 입력을 기다리는 동안 CPU까지 쉬게 할 필요는 없다. 운영체제는 실행 가능한 다른 프로세스를 골라 계산을 진행한다. 따라서 준비 상태와 대기 상태를 먼저 구분해야 한다. 준비 상태는 CPU만 받으면 실행할 수 있는 상태이고, 대기 상태는 입출력 완료 같은 사건을 기다려 아직 실행할 수 없는 상태다.

선점형 스케줄링에서는 운영체제가 실행 중인 프로세스의 CPU를 회수할 수 있다. 타이머 인터럽트가 발생하거나 더 높은 우선순위의 작업이 준비되었을 때 교체 여부를 결정하는 방식이 여기에 속한다. 비선점형 스케줄링에서는 실행 중인 프로세스가 종료되거나 스스로 대기 상태로 들어갈 때까지 CPU를 계속 사용한다. 비선점형이라고 해서 인터럽트가 전혀 발생하지 않는 것은 아니다. 핵심은 준비된 다른 프로세스를 위해 실행권을 강제로 빼앗는지 여부다.

스케줄러는 실행 대상을 결정하고, 디스패처는 그 결정에 따라 실제 전환을 수행한다. 디스패처는 이전 실행 문맥을 저장하고 다음 프로세스의 레지스터와 프로그램 카운터 등을 복구한다. 사용자 모드로 전환해 올바른 명령 위치에서 실행을 재개하는 과정도 필요하다. 이 전환 시간에는 사용자 프로그램의 유용한 계산이 늘지 않으므로 문맥 교환은 공짜가 아니다. 너무 자주 바꾸면 공정해 보이더라도 처리 성능이 나빠질 수 있다.

수업에서 사용하는 준비 큐 그림은 논리적인 선택 후보 집합이다. 실제 구현이 항상 단순한 선입선출 큐인 것은 아니다. 우선순위별 여러 큐나 트리로 관리할 수도 있다. 따라서 그림의 왼쪽에 그려진 프로세스가 반드시 다음 실행 대상이라고 판단하지 않는다. 큐에 들어 있는 순서와 스케줄링 정책을 함께 읽어야 한다. 설명 연습에서는 준비와 대기, 선점과 비선점, 선택과 전환이라는 세 쌍을 구분해 말해 보자.

## 2. 성능을 비교하는 지표

CPU 이용률은 관찰 시간 중 CPU가 작업을 수행한 시간의 비율이다. 처리량은 단위 시간 동안 완료한 프로세스 수다. 두 지표 모두 시스템 전체의 관점이지만 같은 뜻은 아니다. 긴 작업 하나를 계속 실행하면 이용률이 높아도 짧은 관찰 구간의 완료 개수는 작을 수 있다. 또한 CPU가 바쁘다는 사실만으로 사용자가 빠른 반응을 경험했다고 결론 내릴 수 없다.

반환 시간은 프로세스가 도착한 시점부터 종료한 시점까지의 전체 시간이다. 대기 시간은 준비 큐에서 CPU를 기다린 시간을 합한 값이다. 응답 시간은 도착한 시점부터 처음 CPU를 배정받기까지 걸린 시간으로 정의한다. 이 노트의 단순 예제에서는 첫 실행을 첫 응답으로 간주한다. 실제 대화형 서비스에서 사용자가 결과를 보기까지의 지연에는 네트워크나 렌더링 등 다른 단계도 포함될 수 있다.

입출력이 없고 CPU 실행 구간만 있는 예제에서는 반환 시간에서 총 CPU 실행 시간을 빼면 대기 시간이 나온다. 입출력 대기가 존재하는 예제에 이 공식을 그대로 쓰면 준비 큐 대기와 장치 대기를 혼동한다. 풀이 전에 예제의 가정을 확인해야 하는 이유다. 또한 첫 실행 뒤 여러 번 선점되더라도 이미 정해진 응답 시간은 변하지 않는다. 이후의 지연은 대기 시간과 반환 시간에 영향을 준다.

평균값만 낮추는 정책이 모든 사람에게 만족스러운 것은 아니다. 대다수 짧은 작업이 빨리 끝나는 대신 긴 작업 하나가 지나치게 오래 기다릴 수 있다. 그래서 최대 대기 시간, 편차, 기아 가능성 같은 보조 관점도 함께 본다. 온라인 강의의 채팅 입력처럼 짧은 응답이 중요한 작업과 야간 일괄 분석처럼 완료량이 중요한 작업은 우선할 지표가 다르다. 정책을 비교할 때는 먼저 시스템의 목표를 한 문장으로 정해야 한다.

## 3. FCFS와 호위 효과

FCFS는 First Come, First Served의 약자로, 준비 큐에 먼저 들어온 프로세스부터 실행하는 비선점형 정책이다. 도착 순서가 정책의 핵심 정보이며 미래 실행 시간을 예측할 필요가 없다. 구현과 설명이 단순하고 각 작업의 차례가 명확하다는 장점이 있다. 단, 도착 시간이 같다면 입력 순서 같은 별도의 동률 처리 규칙을 정해야 실행 순서가 하나로 결정된다.

긴 CPU 작업 뒤에 짧은 작업이 여러 개 도착하면 짧은 작업은 모두 앞의 긴 작업이 끝나기를 기다린다. 이를 호위 효과라고 부른다. 학과 사무실에서 서류 한 장을 받으려는 학생들이 복잡한 상담 한 건 뒤에 줄 서 있는 상황에 비유할 수 있다. 줄의 순서를 잘 지켰더라도 짧은 업무의 응답은 좋지 않다. 이 사례는 도착 순서의 공정성과 체감 지연이 서로 다른 기준임을 보여 준다.

예를 들어 A의 CPU 사용 시간이 길고 B와 C의 사용 시간이 짧을 때, A가 먼저 도착하면 B와 C의 대기가 커진다. 반대로 짧은 작업들이 먼저 오면 평균 대기가 작아질 수 있다. 작업 집합 자체가 같아도 도착 순서가 성능에 영향을 주는 것이다. FCFS가 항상 나쁘거나 항상 공정하다는 말 대신, 순서가 어떤 부담을 만드는지 설명해야 한다. 수치 비교를 할 때도 완료 순서만 보지 말고 도착 시각을 함께 적는다.

FCFS는 기본형에서 실행을 강제로 끊지 않으므로 시간 할당량을 정하지 않는다. 시간 할당량이 끝날 때마다 큐의 뒤로 보내는 것은 뒤에서 다룰 라운드 로빈의 특징이다. 두 정책 모두 큐를 이용할 수 있어도 전환 조건이 다르다. 어떤 정책인지 헷갈리면 지금 실행 중인 작업이 CPU를 계속 원할 때 누가 중단시킬 수 있는지를 묻는다. 이 질문으로 자료구조와 스케줄링 규칙을 구별할 수 있다.

## 4. SJF와 실행 시간 예측

SJF는 준비된 프로세스 가운데 다음 CPU 버스트가 가장 짧은 것을 고르는 정책이다. 기본 SJF는 비선점형이다. 실행을 시작한 뒤 더 짧은 작업이 도착하더라도 현재 작업의 버스트가 끝나기 전에는 바꾸지 않는다. 남은 실행 시간을 기준으로 새 도착 작업과 비교해 선점하는 변형은 SRTF라고 부른다. 전체 프로그램 길이와 다음 CPU 버스트 길이를 구분하는 것도 중요하다.

모든 작업이 동시에 준비되어 있고 다음 실행 시간을 정확히 안다는 단순 조건에서는 짧은 작업을 먼저 처리하면 평균 대기 시간을 줄일 수 있다. 긴 작업 앞에 짧은 작업을 놓으면 뒤의 긴 작업이 조금 더 기다리는 대신 짧은 작업이 긴 시간 기다리는 일을 피한다. 그러나 도착 시각이 다르고 선점 조건도 다르면 결론을 그대로 적용하지 않는다. 정책의 장점을 말할 때 그 장점이 성립하는 가정을 생략하지 말자.

현실에서는 운영체제가 앞으로의 정확한 CPU 버스트를 미리 알기 어렵다. 과거 실행 구간을 측정해 다음 값을 추정할 수 있지만 추정은 정답과 같지 않다. 최근 관측치에 더 큰 비중을 주면 행동 변화에 빨리 반응하는 대신 변동에 민감해진다. 과거 추세를 크게 반영하면 안정적이지만 새로운 패턴을 따라가는 속도가 느릴 수 있다. 그래서 SJF는 선택 규칙과 예측 문제를 나누어 이해하는 편이 좋다.

짧은 작업이 계속 도착하는 환경에서는 긴 작업의 실행 기회가 뒤로 밀릴 수 있다. 이러한 기아 가능성은 평균 대기가 작다는 설명과 모순되지 않는다. 평균 성능과 개별 작업의 진행 보장은 별개이기 때문이다. 수업 토론에서는 작업 크기 추정이 틀렸을 때 어떤 프로세스가 불리해질지도 생각해 본다. 측정한 값과 미래의 실제 필요량을 같은 것으로 취급하지 않는 태도가 구현 검토에도 도움이 된다.

## 5. 라운드 로빈과 시간 할당량

라운드 로빈은 준비 큐의 프로세스에 시간 할당량만큼 CPU를 번갈아 주는 선점형 정책이다. 할당량이 끝났는데 실행할 내용이 남아 있으면 프로세스를 준비 큐 뒤로 보낸다. 그 전에 작업이 종료되거나 입출력을 요청하면 남은 할당량을 채우기 위해 기다리지 않고 다음 후보를 실행한다. 차례를 순환시킨다는 뜻이지 모든 작업이 언제나 정확히 같은 길이로 실행된다는 뜻은 아니다.

시간 할당량이 매우 크면 대부분의 프로세스가 선점되기 전에 자신의 CPU 버스트를 마치므로 FCFS와 비슷한 동작을 보인다. 반대로 할당량이 작으면 각 프로세스가 첫 실행 기회를 빨리 받을 수 있지만 전환 횟수가 많아진다. 문맥 교환 비용을 고려하면 지나치게 작은 할당량은 실제 계산에 쓰는 비율을 낮출 수 있다. 따라서 작을수록 무조건 좋은 설정이라는 결론은 옳지 않다.

대화형 프로그램에서는 키보드 입력 뒤 빠르게 반응하는 것이 중요하다. 라운드 로빈은 한 프로세스가 CPU를 독점하는 시간을 제한해 다른 작업에도 기회를 준다. 다만 준비 큐에 있는 작업 수가 늘어나면 다음 차례까지의 시간도 길어진다. 할당량 하나만 보고 사용자의 지연을 예측할 수 없는 이유다. 응답을 논할 때는 큐 길이와 전환 비용, 입출력 동작도 함께 고려한다.

간트 차트를 그릴 때는 새 작업의 도착과 현재 할당량의 끝이 같은 시각일 경우의 삽입 순서를 명시한다. 그렇지 않으면 서로 다른 풀이가 모두 그럴듯해 보일 수 있다. 또한 마지막 남은 실행 시간이 할당량보다 짧다면 실제 남은 시간만 실행한다. 노트의 기본 예제에서는 전환 비용을 생략하지만 실험 보고서에는 측정한 오버헤드를 별도로 적는다. 공정한 CPU 배분과 빠른 작업 완료가 항상 동시에 개선되지는 않는다.

## 6. 우선순위와 기아 방지

우선순위 스케줄링은 각 프로세스에 부여한 우선순위를 기준으로 실행 대상을 선택한다. 우선순위 숫자가 작을수록 높은 정책도 있고 반대인 정책도 있으므로 숫자의 의미를 먼저 선언한다. 우선순위는 사용자 지정, 서비스 중요도, 자원 사용 특성 등 여러 근거로 정할 수 있다. 동일 우선순위 안에서는 FCFS나 라운드 로빈 같은 별도의 규칙을 사용할 수 있다.

우선순위 정책은 선점형과 비선점형으로 모두 만들 수 있다. 선점형에서는 더 높은 우선순위 프로세스가 준비되면 현재 실행을 중단할 수 있다. 비선점형에서는 현재 CPU 버스트가 끝난 뒤 다음 대상을 선택할 때 우선순위를 적용한다. 그러므로 우선순위라는 이름만 보고 선점 여부를 판단해서는 안 된다. 선택 기준과 교체 시점을 따로 적으면 정책을 정확하게 설명할 수 있다.

높은 우선순위 작업이 계속 들어오면 낮은 우선순위 작업은 오래 기다리거나 실행 기회를 얻지 못할 수 있다. 이를 기아라고 한다. 에이징은 대기 시간이 늘어날수록 우선순위를 점차 높여 오래 기다린 작업에도 기회를 주는 방법이다. 에이징은 낮은 우선순위 작업을 무조건 먼저 실행한다는 뜻이 아니다. 기다림을 선택 기준에 반영해 영구적으로 밀리는 상황을 줄이는 장치다.

기아와 교착 상태는 다른 현상이다. 기아에서는 시스템의 다른 작업이 계속 진행되면서 특정 작업만 선택되지 않을 수 있다. 교착 상태에서는 자원을 기다리는 관계 때문에 관련 작업들이 서로 진행하지 못한다. 원인과 해결 방식이 다르므로 오래 멈췄다는 관찰만으로 같은 이름을 붙이지 않는다. 장애를 분석할 때는 준비 큐에 있는지, 자원을 기다리는지, 실제로 선택 기회가 있었는지를 확인하는 것이 출발점이다.

## 7. 다단계 큐와 피드백

다단계 큐는 서로 다른 종류의 작업을 여러 준비 큐로 나누고 큐마다 다른 내부 정책을 사용하는 방식이다. 예를 들어 대화형 작업 큐에는 라운드 로빈을, 일괄 작업 큐에는 FCFS를 적용할 수 있다. 큐 내부에서 누구를 고르는지와 큐 사이에 CPU를 어떻게 나누는지는 별개의 결정이다. 큐 사이에 엄격한 우선순위를 적용하면 낮은 큐가 굶을 수 있으므로 전체 구조를 함께 분석한다.

다단계 피드백 큐에서는 작업의 관찰된 행동에 따라 큐 사이의 이동을 허용한다. 짧게 CPU를 사용하고 자주 입출력을 기다리는 작업과 할당량을 계속 소진하는 작업을 다르게 취급할 수 있다. 미래의 정확한 실행 시간을 알지 못하더라도 지난 행동을 정책에 반영한다는 점이 핵심이다. 모든 구현이 같은 큐 개수나 같은 이동 규칙을 사용하는 것은 아니다.

대표적인 설명에서는 새 작업이 높은 큐에서 시작하고 할당량을 끝까지 쓰면 낮은 큐로 내려간다. 오래 기다리는 작업을 다시 위로 올리거나 일정 주기로 모두 재조정하는 정책도 가능하다. 그러나 이 규칙들은 구체적인 설계의 예시이며 이름 자체에 고정된 법칙은 아니다. 보고서에는 큐 수, 각 할당량, 승격과 강등 조건, 큐 사이 선택 순서를 명시해야 실험을 재현할 수 있다.

피드백 정책은 적응성이 있지만 복잡한 상호작용이 생긴다. 작업이 의도적으로 할당량 직전에 양보하면 높은 큐를 유지할 수 있는지, 실제 대화형 작업을 잘 보호하는지 검토해야 한다. 관찰 구간 하나만으로 프로세스의 영구적인 성격을 결정하는 것도 피한다. 수업에서는 단순한 두 큐 모형으로 이동을 추적한 뒤, 어떤 행동이 보상되며 그 보상이 목표와 일치하는지 말로 설명한다.

## 8. 실험과 설명의 점검

스케줄러 비교 실험은 같은 작업 집합과 같은 측정 조건을 사용해야 의미가 있다. 프로세스마다 도착 시각, CPU 버스트, 입출력 구간을 표로 정리하고 동률 처리 규칙을 먼저 정한다. 그런 다음 시간 축 위에 실행 구간과 유휴 구간을 표시한다. 완료 시각만 적으면 중간의 선점과 준비 큐 대기를 복원하기 어려우므로 전환 이유를 함께 남기는 것이 좋다.

정확성 점검의 첫 단계는 어떤 프로세스도 도착하기 전에 실행되지 않았는지 확인하는 것이다. 대기 상태의 프로세스가 선택되지 않았는지, 비선점 정책에서 이유 없이 실행이 끊기지 않았는지도 본다. 모든 CPU 실행 구간을 합하면 요구한 CPU 시간이 되어야 한다. 문맥 교환 비용을 넣었다면 그 구간을 사용자 실행 시간과 겹쳐 세지 않는다. 이 보존 관계는 계산 실수를 빠르게 찾는 데 유용하다.

정책을 평가할 때 평균 대기 시간, 평균 응답 시간, 완료량을 서로 바꾸어 말하지 않는다. 지표가 개선된 원인을 선택 규칙과 연결해 설명한다. 예를 들어 짧은 작업을 앞에 둬 평균 대기가 감소했는지, 실행권을 자주 나눠 첫 반응이 빨라졌는지를 구별한다. 어떤 지표가 나빠졌다면 오류라고 단정하기 전에 다른 목표를 위한 절충인지 살펴본다.

마지막으로 친구에게 정책 하나를 설명할 때 네 가지 질문에 답해 보자. 후보는 누구인지, 선택에 어떤 정보를 쓰는지, 현재 실행을 언제 끊는지, 어떤 작업이 불리한지다. 예제의 숫자를 모두 기억하지 못하더라도 이 질문에 답할 수 있으면 새로운 작업 집합을 분석할 수 있다. 시험 직전에는 이름과 장단점 목록을 반복하기보다 한 정책을 다른 정책과 구별하는 최소 사례를 직접 만들어 설명한다.
