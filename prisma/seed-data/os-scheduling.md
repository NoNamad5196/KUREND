# 운영체제 4장 프로세스 스케줄링

> 강의노트 요약본. 교재는 Silberschatz, Operating System Concepts 10판의 프로세스·CPU 스케줄링 범위에 해당한다. 시험 범위는 1절부터 6절까지이며, 간트 차트를 그리고 평균 대기 시간을 계산하는 문제는 반드시 손으로 풀어 볼 것.

## 1. 프로세스와 스레드

### 1.1 프로세스의 개념

- 프로세스(process): 실행 중인 프로그램. 디스크에 저장된 프로그램은 수동적인 개체이고, 메모리에 적재되어 실행되는 프로세스는 능동적인 개체이다.
- 프로세스의 메모리 구성: 텍스트(코드) 영역, 데이터 영역(전역 변수), 힙(실행 중 동적으로 할당되는 메모리), 스택(함수 호출 정보와 지역 변수)
- 같은 프로그램을 두 번 실행하면 코드는 같지만 데이터·힙·스택이 서로 다른 두 개의 프로세스가 만들어진다.

### 1.2 프로세스 상태 전이

프로세스는 실행되는 동안 다음 다섯 가지 상태 중 하나에 있다.

- new(생성): 프로세스가 막 생성되는 중인 상태
- ready(준비): CPU를 할당받기 위해 준비 큐에서 기다리는 상태
- running(실행): 명령어가 CPU에서 실제로 실행되고 있는 상태
- waiting(대기): 입출력 완료나 특정 이벤트 발생을 기다리는 상태
- terminated(종료): 실행이 끝난 상태

상태 사이의 전이는 다음과 같다. 단일 코어 시스템에서 running 상태의 프로세스는 한 순간에 하나뿐이지만 ready와 waiting 상태의 프로세스는 여러 개일 수 있다.

- new → ready: 생성이 끝나 준비 큐에 들어갈 때(admit)
- ready → running: 스케줄러가 선택해 CPU를 배정할 때(dispatch)
- running → ready: 시간 할당량이 끝나거나 인터럽트로 CPU를 빼앗길 때(선점)
- running → waiting: 입출력 요청이나 이벤트 대기로 스스로 CPU를 내놓을 때
- waiting → ready: 입출력이 완료되거나 기다리던 이벤트가 발생했을 때
- running → terminated: exit 시스템 호출 등으로 실행을 마칠 때

주의: waiting 상태에서 곧바로 running으로 갈 수는 없다. 입출력이 끝나면 반드시 ready 상태를 거쳐 다시 스케줄러의 선택을 받아야 한다.

### 1.3 프로세스 제어 블록(PCB)

- PCB(Process Control Block): 운영체제가 프로세스마다 하나씩 유지하는 자료구조로, 프로세스에 관한 모든 정보를 담는다. 리눅스에서는 task_struct가 이에 해당한다.
- 주요 내용: 프로세스 상태, 프로세스 번호(PID), 프로그램 카운터, CPU 레지스터 값, CPU 스케줄링 정보(우선순위, 큐 포인터), 메모리 관리 정보(페이지 테이블, 기준·한계 레지스터), 회계 정보(사용한 CPU 시간), 입출력 상태 정보(열린 파일 목록, 할당된 장치)
- 프로세스가 CPU를 빼앗길 때 현재의 실행 문맥이 PCB에 저장되고, 다시 CPU를 얻을 때 PCB에서 복원된다.

### 1.4 컨텍스트 스위칭

- 컨텍스트 스위칭(context switch, 문맥 교환): CPU를 한 프로세스에서 다른 프로세스로 넘길 때, 현재 프로세스의 문맥을 PCB에 저장하고 다음 프로세스의 문맥을 PCB에서 복원하는 작업
- 문맥 교환 시간은 순수한 오버헤드다. 교환하는 동안 시스템은 유용한 일을 하지 못한다. 보통 수 마이크로초 단위이며 하드웨어 지원(레지스터 세트 수, 메모리 속도)에 따라 달라진다.
- 교환 비용이 큰 이유: 레지스터 저장·복원뿐 아니라 캐시와 TLB(주소 변환 캐시)의 내용이 무효화되어 새 프로세스가 초기에 캐시 미스를 많이 겪기 때문이다.

### 1.5 스레드

- 스레드(thread): CPU 이용의 기본 단위. 스레드 ID, 프로그램 카운터, 레지스터 집합, 스택을 따로 가지며, 같은 프로세스의 다른 스레드와 코드·데이터·열린 파일 등을 공유한다.
- 현대 운영체제에서 실제 스케줄링 단위는 프로세스가 아니라 커널 스레드다. 이 장에서 "프로세스 스케줄링"이라 할 때 사실상 커널 스레드 스케줄링을 뜻한다.
- 같은 프로세스 안의 스레드끼리 전환하면 주소 공간을 바꾸지 않아도 되므로 프로세스 간 문맥 교환보다 비용이 작다.

## 2. 스케줄링의 개념과 기준

### 2.1 CPU 스케줄링의 필요성

- 다중 프로그래밍의 목적은 CPU 이용률을 최대화하는 것이다. 어떤 프로세스가 입출력을 기다리는 동안 CPU를 놀리지 않고 다른 프로세스에 넘겨 준다.
- CPU 스케줄러(단기 스케줄러): 준비 큐에 있는 프로세스 중 다음에 실행할 것을 고르는 운영체제 구성 요소. 매우 자주 호출되므로 빠르게 결정을 내려야 한다.

### 2.2 CPU 버스트와 I/O 버스트

- 프로세스 실행은 CPU 버스트(CPU burst)와 I/O 버스트(I/O burst)가 번갈아 나타나는 주기로 이루어진다. CPU 버스트로 시작해 CPU 버스트로 끝난다.
- CPU 버스트 길이의 분포를 측정하면 대체로 지수 분포 혹은 초지수 분포 형태를 띤다. 짧은 CPU 버스트가 매우 많고, 긴 CPU 버스트는 드물다.
- CPU 지향(CPU-bound) 프로세스는 긴 CPU 버스트가 적게 나타나고, 입출력 지향(I/O-bound) 프로세스는 짧은 CPU 버스트가 많이 나타난다.

### 2.3 선점 스케줄링과 비선점 스케줄링

스케줄링 결정은 다음 네 가지 상황에서 일어난다.

1. 프로세스가 running에서 waiting으로 바뀔 때(입출력 요청, wait 호출)
2. 프로세스가 running에서 ready로 바뀔 때(인터럽트 발생)
3. 프로세스가 waiting에서 ready로 바뀔 때(입출력 완료)
4. 프로세스가 종료될 때

- 비선점(non-preemptive) 스케줄링: 1번과 4번 상황에서만 스케줄링한다. 프로세스가 CPU를 할당받으면 종료하거나 대기 상태로 바뀔 때까지 CPU를 점유한다. 협조적(cooperative) 스케줄링이라고도 한다.
- 선점(preemptive) 스케줄링: 2번과 3번 상황에서도 스케줄링한다. 운영체제가 실행 중인 프로세스에서 CPU를 강제로 빼앗을 수 있다. 공유 데이터를 갱신하는 도중에 선점되면 경쟁 조건이 생길 수 있어 동기화가 필요하고, 타이머 하드웨어가 있어야 한다.
- Windows, macOS, Linux 등 거의 모든 현대 운영체제는 선점 스케줄링을 사용한다.

### 2.4 디스패처

- 디스패처(dispatcher): CPU 스케줄러가 선택한 프로세스에게 실제로 CPU 제어권을 넘겨주는 모듈. 문맥 교환, 사용자 모드로 전환, 프로그램을 재개할 위치로 점프하는 일을 한다.
- 디스패치 지연(dispatch latency): 한 프로세스를 정지시키고 다른 프로세스의 실행을 시작할 때까지 걸리는 시간. 디스패처는 매 문맥 교환마다 호출되므로 가능한 한 빨라야 한다.

### 2.5 스케줄링 평가 기준

| 기준 | 정의 | 목표 |
|---|---|---|
| CPU 이용률(utilization) | CPU가 일하는 시간의 비율 | 최대화 |
| 처리량(throughput) | 단위 시간당 완료되는 프로세스 수 | 최대화 |
| 반환 시간(turnaround time) | 제출부터 완료까지 걸린 총 시간 | 최소화 |
| 대기 시간(waiting time) | 준비 큐에서 기다린 시간의 합 | 최소화 |
| 응답 시간(response time) | 요청 제출부터 첫 응답이 나올 때까지의 시간 | 최소화 |

- 반환 시간 = 종료 시각 − 도착 시각. 입출력이 없다고 가정하면 대기 시간 = 반환 시간 − CPU 버스트 시간이다.
- 응답 시간은 첫 응답을 내기 시작할 때까지의 시간이지 출력이 끝날 때까지의 시간이 아니다. 대화형 시스템에서는 평균보다 분산이 작은 것이 더 중요하다. 예측 가능한 응답이 빠르지만 들쭉날쭉한 응답보다 낫다.
- 일반적으로 평균값을 최적화하지만, 공정성을 위해 최대 대기 시간을 줄이는 쪽이 바람직할 때도 있다.

## 3. CPU 스케줄링 알고리즘

이 절에서는 CPU 코어가 하나인 단일 처리기를 가정하고, 각 알고리즘을 프로세스 집합에 적용해 평균 대기 시간을 비교한다. 시험에서는 간트 차트를 직접 그리고 대기 시간을 계산하는 문제가 반드시 나온다.

### 3.1 선입 선처리 스케줄링(FCFS)

- FCFS(First-Come, First-Served): CPU를 요청한 순서대로 할당한다. FIFO 큐로 간단히 구현하며 비선점 방식이다.
- 예시: 세 프로세스가 시각 0에 P1, P2, P3 순서로 도착했고 CPU 버스트가 각각 24, 3, 3이라고 하자.

간트 차트: | P1 (0~24) | P2 (24~27) | P3 (27~30) |

- 대기 시간: P1 = 0, P2 = 24, P3 = 27. 평균 대기 시간 = (0 + 24 + 27) / 3 = 17
- 도착 순서가 P2, P3, P1이었다면 대기 시간은 P2 = 0, P3 = 3, P1 = 6이 되어 평균 대기 시간은 (0 + 3 + 6) / 3 = 3으로 줄어든다. 도착 순서에 따라 결과가 크게 달라진다.
- 호위 효과(convoy effect): CPU 버스트가 긴 프로세스 하나가 CPU를 잡고 있으면, 짧은 입출력 지향 프로세스들이 모두 그 뒤에 줄지어 기다리게 되는 현상. CPU와 입출력 장치의 이용률이 모두 떨어진다.
- 비선점이므로 시분할 시스템에는 적합하지 않다.

### 3.2 최단 작업 우선 스케줄링(SJF)

- SJF(Shortest-Job-First): 다음 CPU 버스트가 가장 짧은 프로세스에 CPU를 먼저 할당한다. 정확히는 "최단 다음 CPU 버스트 우선"이다. 버스트 길이가 같으면 FCFS로 결정한다.
- 예시: 시각 0에 모두 도착, CPU 버스트 P1 = 6, P2 = 8, P3 = 7, P4 = 3

간트 차트: | P4 (0~3) | P1 (3~9) | P3 (9~16) | P2 (16~24) |

- 대기 시간: P4 = 0, P1 = 3, P3 = 9, P2 = 16. 평균 대기 시간 = (0 + 3 + 9 + 16) / 4 = 7
- 같은 집합을 FCFS(P1, P2, P3, P4 순)로 돌리면 대기 시간은 0, 6, 14, 21이 되어 평균 대기 시간은 10.25다.
- SJF는 주어진 프로세스 집합에 대해 평균 대기 시간이 최소라는 점에서 최적(optimal)이다. 짧은 프로세스를 앞으로 옮기면 긴 프로세스의 대기 시간이 늘어나는 양보다 짧은 프로세스들의 대기 시간이 줄어드는 양이 더 크기 때문이다.
- 문제점: 다음 CPU 버스트의 길이를 미리 알 수 없다. 그래서 과거 버스트 길이의 지수 평균(exponential average)으로 예측한다. τ(n+1) = α × t(n) + (1 − α) × τ(n)이며, t(n)은 n번째 실제 버스트 길이, τ(n)은 n번째 예측값, 0 ≤ α ≤ 1이다. α = 1/2이면 최근 실제값과 이전 예측값을 같은 비중으로 반영하고, α = 1이면 직전 버스트 길이만 사용한다.

### 3.3 최소 잔여 시간 우선 스케줄링(SRTF)

- SRTF(Shortest-Remaining-Time-First): SJF의 선점형 버전. 새 프로세스가 준비 큐에 도착했을 때 그 프로세스의 CPU 버스트가 현재 실행 중인 프로세스의 남은 시간보다 짧으면 CPU를 빼앗는다.
- 예시: (도착 시각, CPU 버스트)가 P1 = (0, 8), P2 = (1, 4), P3 = (2, 9), P4 = (3, 5)

간트 차트: | P1 (0~1) | P2 (1~5) | P4 (5~10) | P1 (10~17) | P3 (17~26) |

- 시각 1에 P2가 도착했을 때 P1의 남은 시간은 7, P2의 버스트는 4이므로 P2가 P1을 선점한다. 시각 2에 도착한 P3(9)와 시각 3에 도착한 P4(5)는 P2의 남은 시간보다 길어 선점하지 못한다.
- 대기 시간 = 반환 시간 − 버스트 시간: P1 = 17 − 0 − 8 = 9, P2 = 5 − 1 − 4 = 0, P3 = 26 − 2 − 9 = 15, P4 = 10 − 3 − 5 = 2
- 평균 대기 시간 = (9 + 0 + 15 + 2) / 4 = 6.5. 같은 집합을 비선점 SJF로 돌리면 평균 대기 시간은 7.75다.

### 3.4 우선순위 스케줄링

- 우선순위(priority) 스케줄링: 각 프로세스에 우선순위를 부여하고 우선순위가 가장 높은 프로세스에 CPU를 할당한다. 우선순위가 같으면 FCFS 순서로 처리한다.
- 우선순위는 보통 정수로 나타내며, 이 교재에서는 숫자가 작을수록 우선순위가 높다고 약속한다. 시스템마다 반대인 경우도 있으므로 문제에서 반드시 확인할 것.
- SJF는 다음 CPU 버스트 길이를 우선순위로 삼는 우선순위 스케줄링의 특수한 경우다.
- 선점형과 비선점형이 모두 가능하다. 선점형에서는 새로 도착한 프로세스의 우선순위가 실행 중인 프로세스보다 높으면 CPU를 빼앗는다.
- 예시: 시각 0에 모두 도착, (CPU 버스트, 우선순위)가 P1 = (10, 3), P2 = (1, 1), P3 = (2, 4), P4 = (1, 5), P5 = (5, 2)

간트 차트: | P2 (0~1) | P5 (1~6) | P1 (6~16) | P3 (16~18) | P4 (18~19) |

- 대기 시간: P1 = 6, P2 = 0, P3 = 16, P4 = 18, P5 = 1. 평균 대기 시간 = (6 + 0 + 16 + 18 + 1) / 5 = 8.2

### 3.5 기아와 에이징

- 기아(starvation, 무한 봉쇄): 우선순위가 낮은 프로세스가 더 높은 우선순위의 프로세스에 계속 밀려 무한정 CPU를 받지 못하는 문제. 부하가 큰 시스템에서는 높은 우선순위 프로세스가 끊임없이 들어오므로 낮은 우선순위 프로세스는 영원히 실행되지 못할 수 있다.
- 1973년 MIT의 IBM 7094를 폐기할 때 1967년에 제출되었던 낮은 우선순위 프로세스가 아직도 실행되지 못한 채 발견되었다는 일화가 있다.
- 에이징(aging): 기아의 해결책. 준비 큐에서 오래 기다린 프로세스의 우선순위를 시간에 비례해 점진적으로 높여 준다. 예를 들어 우선순위가 0(높음)부터 127(낮음)까지 있을 때 15분마다 대기 중인 프로세스의 우선순위를 1씩 올리면, 처음 127이었던 프로세스도 32시간 이내에 우선순위 0이 되어 결국 실행된다.
- 우선순위 스케줄링과 라운드 로빈을 결합할 수도 있다. 우선순위가 가장 높은 프로세스를 실행하되, 우선순위가 같은 프로세스들끼리는 라운드 로빈으로 돌린다.

## 4. 라운드 로빈과 시간 할당량

### 4.1 라운드 로빈 스케줄링(RR)

- 라운드 로빈(Round-Robin, RR): 시분할 시스템을 위해 설계된 선점형 알고리즘. FCFS와 비슷하지만 프로세스 사이를 전환할 수 있도록 시간 할당량(time quantum, time slice)이라는 작은 단위 시간을 정의한다. 보통 10~100ms다.
- 준비 큐는 원형 큐로 동작한다. 스케줄러는 준비 큐를 돌면서 각 프로세스에 최대 1 시간 할당량 동안 CPU를 할당한다.
- 두 가지 경우가 생긴다. 첫째, 프로세스의 CPU 버스트가 시간 할당량보다 짧으면 프로세스가 스스로 CPU를 내놓고 스케줄러는 다음 프로세스로 넘어간다. 둘째, 버스트가 시간 할당량보다 길면 타이머 인터럽트가 발생해 문맥 교환이 일어나고, 프로세스는 준비 큐의 꼬리에 들어간다.
- 예시: 시각 0에 도착, CPU 버스트 P1 = 24, P2 = 3, P3 = 3, 시간 할당량 = 4

간트 차트: | P1 (0~4) | P2 (4~7) | P3 (7~10) | P1 (10~14) | P1 (14~18) | P1 (18~22) | P1 (22~26) | P1 (26~30) |

- 대기 시간: P1 = 10 − 4 = 6, P2 = 4, P3 = 7. 평균 대기 시간 = (6 + 4 + 7) / 3 = 17 / 3 ≈ 5.67
- RR의 평균 대기 시간은 대체로 긴 편이다. 대신 준비 큐에 n개의 프로세스가 있고 시간 할당량이 q이면, 각 프로세스는 최대 (n − 1) × q 시간만 기다리면 다음 차례를 보장받는다. 따라서 기아가 생기지 않는다.

### 4.2 시간 할당량 크기의 영향

- 시간 할당량이 매우 크면(무한대에 가까우면) RR은 FCFS와 같아진다.
- 시간 할당량이 매우 작으면(예: 1ms) 프로세서 공유(processor sharing)처럼 보여 n개의 프로세스가 각각 속도 1/n인 CPU를 가진 것처럼 느끼게 된다. 하지만 문맥 교환이 너무 자주 일어나 오버헤드가 커진다.
- 예시: CPU 버스트가 10인 프로세스 하나를 생각하자. 시간 할당량이 12이면 문맥 교환이 0번, 6이면 1번, 1이면 9번 일어난다. 시간 할당량이 작아질수록 문맥 교환 횟수가 늘어난다.
- 경험 법칙: 시간 할당량은 문맥 교환 시간보다 충분히 커야 한다. 문맥 교환 시간이 시간 할당량의 약 10%라면 CPU 시간의 10%가 오버헤드로 쓰이는 셈이다. 현대 시스템은 시간 할당량 10~100ms, 문맥 교환 시간 10μs 이하 정도로 설계한다. 일반적으로 CPU 버스트의 80% 정도가 시간 할당량보다 짧도록 정한다.
- 반환 시간과의 관계: 시간 할당량이 커진다고 평균 반환 시간이 항상 좋아지지는 않는다. 예를 들어 CPU 버스트가 각각 10인 세 프로세스를 시간 할당량 1로 돌리면 세 프로세스가 거의 동시에 끝나 평균 반환 시간이 29이지만, 시간 할당량 10으로 돌리면 10, 20, 30에 끝나 평균 반환 시간이 20으로 줄어든다. 반면 버스트가 6, 3, 1, 7인 네 프로세스는 시간 할당량이 1일 때 평균 반환 시간 11.0, 2일 때 11.5, 3일 때 10.75, 4일 때 11.5, 5일 때 12.25, 6 이상일 때 10.5로 단조롭게 변하지 않는다. 대부분의 프로세스가 한 번의 시간 할당량 안에 CPU 버스트를 끝낼 수 있을 때 평균 반환 시간이 좋아진다.

## 5. 다단계 큐와 다단계 피드백 큐

### 5.1 다단계 큐 스케줄링(MLQ)

- 다단계 큐(Multilevel Queue): 준비 큐를 여러 개의 별도 큐로 분할한다. 프로세스는 메모리 크기, 우선순위, 유형 같은 속성에 따라 하나의 큐에 영구적으로 배정된다.
- 전형적인 구분은 전경(foreground, 대화형) 프로세스와 배경(background, 일괄 처리) 프로세스다. 두 부류는 응답 시간 요구가 달라 다른 스케줄링이 필요하다. 전경 큐는 RR, 배경 큐는 FCFS로 돌리는 식이다.
- 큐 사이의 스케줄링도 필요하다. 보통 고정 우선순위 선점 스케줄링을 쓴다. 예를 들어 우선순위가 높은 순서로 실시간 프로세스, 시스템 프로세스, 대화형 프로세스, 일괄 처리 프로세스 큐를 두면, 일괄 처리 큐의 프로세스는 위의 세 큐가 모두 비어 있을 때만 실행되고, 실행 중이더라도 상위 큐에 프로세스가 들어오면 선점당한다.
- 다른 방법은 큐 사이에 CPU 시간을 나누어 주는 것이다. 예를 들어 CPU 시간의 80%를 전경 큐에, 20%를 배경 큐에 배정한다.
- 단점: 프로세스가 큐를 옮길 수 없어 융통성이 없다. 한 번 배경 큐에 들어간 프로세스는 성격이 바뀌어도 계속 그 큐에 머무른다. 고정 우선순위를 쓰면 하위 큐에서 기아가 생길 수 있다.

### 5.2 다단계 피드백 큐 스케줄링(MLFQ)

- 다단계 피드백 큐(Multilevel Feedback Queue): 프로세스가 큐 사이를 이동할 수 있게 한다. CPU 버스트 성격에 따라 프로세스를 분류하며, CPU를 너무 많이 쓰는 프로세스는 낮은 우선순위 큐로 내리고 오래 기다린 프로세스는 높은 우선순위 큐로 올린다. 이 승격이 곧 에이징이다.
- 예시: 큐 0, 큐 1, 큐 2 세 개의 큐가 있고 번호가 작을수록 우선순위가 높다. 큐 0은 시간 할당량 8ms의 RR, 큐 1은 시간 할당량 16ms의 RR, 큐 2는 FCFS다.
- 큐 간 이동 규칙:
  1. 새로 들어온 프로세스는 큐 0에 들어간다.
  2. 큐 0에서 8ms 안에 CPU 버스트를 끝내지 못하면 선점되어 큐 1의 꼬리로 내려간다.
  3. 큐 1에서 16ms 안에 끝내지 못하면 큐 2로 내려간다.
  4. 상위 큐가 비어 있을 때만 하위 큐의 프로세스가 실행되며, 상위 큐에 프로세스가 도착하면 실행 중인 하위 큐 프로세스는 선점당한다.
  5. 큐 2에서 오래 기다린 프로세스는 에이징으로 상위 큐로 올라갈 수 있다.
- 효과: CPU 버스트가 8ms 이하인 프로세스(대화형, 입출력 지향)는 큐 0에서 최고 우선순위로 빠르게 처리된다. 8ms 초과 24ms 이하인 프로세스도 비교적 빨리 서비스받는다. 긴 CPU 버스트의 프로세스는 큐 2로 내려가 남는 CPU 시간을 FCFS로 받는다.
- MLFQ를 정의하는 매개변수: 큐의 개수, 각 큐의 스케줄링 알고리즘, 프로세스를 상위 큐로 올리는 기준, 하위 큐로 내리는 기준, 프로세스가 처음 들어갈 큐를 결정하는 방법
- 가장 일반적이지만 가장 복잡한 알고리즘이다. 특정 시스템에 맞추려면 매개변수를 잘 골라야 한다.

## 6. 멀티프로세서 스케줄링과 평가

### 6.1 멀티프로세서 스케줄링 방식

- 비대칭 다중 처리(asymmetric multiprocessing): 하나의 처리기(마스터 서버)만 스케줄링과 입출력 등 시스템 활동을 담당하고 나머지는 사용자 코드만 실행한다. 데이터 공유가 간단하지만 마스터가 병목이 될 수 있다.
- 대칭 다중 처리(SMP, symmetric multiprocessing): 각 처리기가 스스로 스케줄링한다. 모든 스레드를 하나의 공통 준비 큐에 두는 방법과 처리기마다 전용 준비 큐를 두는 방법이 있다. 공통 큐는 경쟁 조건 때문에 잠금이 필요해 병목이 되므로, 현대 운영체제는 대부분 처리기별 큐를 쓴다.

### 6.2 처리기 친화성

- 처리기 친화성(processor affinity): 스레드가 다른 처리기로 이동하면 원래 처리기의 캐시 내용을 무효화하고 새 처리기의 캐시를 다시 채워야 하므로 비용이 크다. 그래서 대부분의 SMP 시스템은 스레드를 같은 처리기에서 계속 실행하려 한다.
- 소프트 친화성(soft affinity): 운영체제가 같은 처리기에서 실행하려고 노력하지만 보장하지는 않는다.
- 하드 친화성(hard affinity): 프로세스가 실행될 수 있는 처리기 집합을 시스템 호출로 지정한다. 리눅스의 sched_setaffinity()가 그 예이다.
- NUMA(Non-Uniform Memory Access) 시스템에서는 처리기가 자기 로컬 메모리에 더 빨리 접근하므로, 스레드를 그 메모리가 있는 노드의 처리기에 배정하는 것이 유리하다.

### 6.3 부하 균형

- 부하 균형(load balancing): 처리기별 준비 큐를 쓰는 SMP에서 한 처리기만 바쁘고 다른 처리기는 노는 상황을 막기 위해 작업 부하를 고르게 분산하는 것.
- 푸시 이주(push migration): 특정 태스크가 주기적으로 각 처리기의 부하를 검사해 과부하된 처리기의 스레드를 한가한 처리기로 밀어낸다.
- 풀 이주(pull migration): 한가한 처리기가 바쁜 처리기의 큐에서 대기 중인 스레드를 끌어온다. 리눅스 CFS와 FreeBSD ULE는 두 방식을 모두 쓴다.
- 부하 균형과 처리기 친화성은 서로 충돌한다. 스레드를 옮기면 부하는 고르게 되지만 캐시 친화성의 이점은 사라진다. 운영체제는 둘 사이의 균형을 잡아야 한다.

### 6.4 알고리즘 평가 방법

- 결정론적 모델링(deterministic modeling): 미리 정해진 특정 작업 부하를 각 알고리즘에 적용해 평균 대기 시간 같은 성능을 계산한다. 3절에서 한 계산이 바로 이것이다. 간단하고 빠르며 정확한 숫자를 주지만, 그 입력에 대해서만 결과가 유효하다.
- 큐잉 모델(queueing model): CPU 버스트와 도착 간격을 확률 분포로 두고 수학적으로 분석한다. 리틀의 공식(Little's formula) n = λ × W가 대표적이다. n은 큐의 평균 길이, λ는 평균 도착률, W는 큐에서의 평균 대기 시간이다. 예를 들어 초당 평균 7개의 프로세스가 도착하고 큐에 평균 14개가 있으면 평균 대기 시간은 2초다.
- 시뮬레이션(simulation): 컴퓨터 시스템의 모델을 프로그램으로 만들고, 난수 생성기나 실제 시스템에서 수집한 추적 파일(trace file)로 프로세스 도착과 버스트를 흉내 내 성능을 측정한다. 큐잉 모델보다 정확하지만 비용이 많이 든다.
- 구현(implementation): 실제로 알고리즘을 운영체제에 넣어 돌려 보는 방법. 가장 정확하지만 비용이 가장 크고, 사용자가 알고리즘에 맞춰 행동을 바꾸는 문제가 있다.

### 6.5 정리

- FCFS는 단순하지만 호위 효과가 있고, SJF는 최적이지만 버스트 예측이 필요하며, 우선순위는 기아 위험이 있어 에이징으로 해결하고, RR은 시분할에 적합하며 시간 할당량 선택이 핵심이다.
- MLFQ는 큐 간 이동으로 위 알고리즘들을 결합한 가장 일반적인 방식이다.
- 멀티프로세서에서는 친화성과 부하 균형 사이의 균형을, 평가에서는 결정론적 모델링·큐잉 모델·시뮬레이션·구현의 장단점을 기억하자.
