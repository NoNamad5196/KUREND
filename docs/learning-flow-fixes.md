# 학습 흐름과 LLM 출력 규칙 수정

이번 변경은 자료 추출, 인증 상태 유지, 학습 대화와 시험 출력의 경계를 수정합니다. 캐릭터별 객관식·서술형 구분, 합격선 60/70/80점, 이해·기억 방식, LIFE·졸업 규칙은 유지합니다. 새 챕터 세션의 학습 목표와 시험 문항은 각각 5개로 맞춥니다.

## 1. 자료 추출 로딩 중앙 정렬

기존 로딩 카드는 페이지 콘텐츠 안에 배치되어 헤더 높이와 부모 레이아웃의 영향을 받았습니다. 추출 중에는 `document.body`에 포털을 만들고 `position: fixed; inset: 0` 영역에서 중앙 정렬합니다. 짧은 화면에서는 스크롤할 수 있으며, 추출이 멈추거나 실패하면 원래 페이지로 돌아와 재시도·삭제 조작을 유지합니다. 책·별 애니메이션은 변경하지 않았습니다.

주요 파일: `src/components/material/MaterialPreparation.tsx`, `src/components/material/material-preparation.css`.

## 2. 갑작스러운 재로그인 조사와 수정

이 앱은 Supabase Auth나 브라우저 저장소의 access/refresh token을 사용하지 않습니다. 인증은 30일 만료가 포함된 HMAC 서명 HttpOnly 쿠키와 DB의 사용자 조회로 이루어집니다. `localStorage`는 화면 설정·학습 보조 상태에 사용되며 인증 원본이 아닙니다. API 요청은 `no-store`이고, middleware는 개발용 API 경로만 제한합니다.

코드와 임시 DB에서 다음 경로를 재현했습니다.

1. 서명과 만료가 정상인 쿠키로 로그인 상태를 확인합니다.
2. DB에서 해당 사용자 행이 사라지면 기존 `requireUser`는 이를 만료로 판단해 401을 반환했습니다.
3. AppShell은 401을 받아 로그인 화면으로 이동했습니다. 이 경우 쿠키 만료가 아니라 계정 저장소의 문제입니다.

현재 `render.yaml`의 기본값은 무료 인스턴스의 로컬 SQLite입니다. 원격 libSQL/Turso 환경변수를 설정하면 원격 DB를 사용할 수 있습니다. 로컬 기본값으로 운영 중 배포·인스턴스 교체에 따라 DB 파일이 사라지면 시작 스크립트가 시드 DB를 만들지만 기존 Google 사용자와 학습 기록은 복원되지 않습니다. 이 구성은 위 재현 경로를 만들 수 있습니다. **운영 로그와 실제 DB 보존 상태를 확인하지 못했으므로 사용자에게 발생한 장애의 원인을 확정하지 않습니다.**

별도로 AppShell은 경로마다 `key`를 바꿔 인증 상태와 하위 화면 전체를 재생성했습니다. 이는 쿠키 삭제의 원인은 아니지만 정상적인 페이지 이동에서도 로그인 확인 로딩과 클라이언트 상태 초기화를 반복했습니다.

수정 사항:

- 정상 서명 쿠키의 계정 유실 또는 서명키 설정 누락은 `AUTH_UNAVAILABLE` 503으로 구분합니다. 계정을 임의로 다시 만들거나 인증 검증을 우회하지 않습니다.
- 실제 만료·변조·쿠키 부재는 계속 401입니다. 30일 만료, HMAC 검증과 운영 쿠키의 `Secure` 설정은 유지합니다.
- 경로 전환에서는 확인된 사용자 상태를 유지합니다. 일시적인 네트워크 오류·503은 로그인으로 보내지 않고 재시도할 수 있게 합니다.
- 탭 복귀와 focus에서 서버 상태를 다시 확인합니다. 최초 보호 화면은 인증 확인 전 표시하지 않으며, 실제 로그아웃·계정 변경 때에는 이전 계정의 화면 상태를 폐기합니다.
- 계정을 바꾼 뒤 이전 계정의 홈 통계·진행 상태 요청이 늦게 완료되어도 새 계정 화면에 반영하지 않습니다. run 변경 이벤트에 따른 요청에도 같은 검증을 적용합니다.
- 원인 로그는 `ACCOUNT_NOT_FOUND`, `SIGNING_KEY_MISSING`, `EXPIRED_SESSION`, `INVALID_SESSION`만 구분합니다. 쿠키·서명키·사용자 ID·이름·DB 경로는 로그에 포함하지 않습니다.
- LLM API의 인증 연결도 503을 그대로 전달하여 모델 오류나 로그인 만료로 바꾸지 않습니다.

주요 파일: `src/lib/server/auth.ts`, `src/lib/server/http.ts`, `src/lib/server/llm-backend.ts`, `src/components/shell/AppShell.tsx`.

**남은 운영 조치:** DB를 보존하는 저장소와 배포 설정, 모든 인스턴스의 동일한 서명키 사용 여부를 확인해야 합니다. 이번 코드 변경은 이미 소실된 DB를 복원하거나 Render에 영속 디스크를 추가하지 않습니다. 구체적인 확인 절차는 [Render 배포 안내](render.md)를 참고하세요.

## 3. 반복되는 “선배님” 호칭

기존 persona에 “항상 선배님”, 대화 프롬프트에 “반드시 선배님”이 명시되어 있었고, 기본 질문과 완료 문구도 같은 호칭을 붙였습니다. 남학생은 자연스러운 `~습니다`, 여학생은 친근한 `~요`를 유지하되 리액션에는 호칭을 붙이지 않도록 수정했습니다. 직접 질문하거나 도움을 청할 때만 가끔 호칭을 허용합니다.

`normalizePersonaAddress`는 리액션이나 반복 호칭의 직접 호출 부분만 정리합니다. 인용된 사용자 설명과 일반적인 역할 명사는 보존하며, KU의 기존 말투·호칭 처리 규칙은 바꾸지 않습니다.

주요 파일: `src/lib/llm/personas.ts`, `src/lib/llm/prompts/respond-turn.ts`, `src/lib/llm/live.ts`, `src/lib/llm/stub.ts`, `src/components/game/characters.ts`, `src/components/session/teach/ChatThread.tsx`.

## 4. 캐릭터별 시험 직전 문구

시험 직전에는 모든 캐릭터에 동일한 반말 문구를 사용했습니다. 이제 남학생은 “지금까지 알려주신 내용으로 한번 풀어보겠습니다!”, 여학생은 “지금까지 알려주신 내용으로 한번 풀어볼게요!”를 사용합니다. KU의 기존 문구는 그대로 유지합니다.

문구와 캐릭터 표시는 세션에 저장된 캐릭터를 우선하고, 없을 때 run 정보를 사용합니다. 캐릭터를 조회 중일 때 잘못된 기본 문구를 먼저 표시하지 않습니다.

성적표의 후배 대사에도 남학생은 `~습니다`, 여학생은 `~요`를 적용하고 KU의 기존 문구는 유지합니다.

주요 파일: `src/components/exam/pages/ExamPage.tsx`, `src/components/exam/pages/ResultPage.tsx`.

## 5. 시험 문제의 대화체 제거

기존 준비 프롬프트와 입력에는 시험 문제와 첫 학습 질문, persona의 말투가 함께 들어갔습니다. 시험 출제 프롬프트에서 persona와 첫 대화를 분리하고, 문제는 `설명하시오.`, `비교하시오.`, `고르시오.` 등의 정식 문장으로 생성하도록 변경했습니다.

출력 스키마에서 문제 형식과 호칭·대화체 사용 여부를 검증합니다. 첫 학습 질문은 준비된 개념을 바탕으로 `personaQuestion`에서 별도로 만듭니다. 기존에 저장된 문제의 표시에는 `formatExamQuestion`을 적용하며 DB의 시험을 재생성하지 않습니다.

주요 파일: `src/lib/llm/prompts/prepare-session.ts`, `src/lib/llm/live.ts`, `src/lib/llm/schemas.ts`, `src/lib/shared/exam-format.ts`, `src/lib/server/session-dto.ts`.

## 6. Markdown 강조 기호 방지

기존 프롬프트에는 강조 문법을 금지하는 공통 규칙이 없었고, UI도 모델 문자열을 그대로 표시했습니다. 생성·재시도 프롬프트에 다음 규칙을 적용합니다.

```text
Do not use Markdown bold syntax (**text**) under any circumstances.
```

`stripMarkdownBold`는 일반 문장의 강조 구분자를 제거합니다. 서버의 생성 출력과 표시용 DTO, 채팅·시험·채점·오답·학습노트 UI에 적용하여 저장된 출력과 스트리밍 중간 조각도 방어합니다. 스트리밍 끝의 미완성 강조 구분자가 먼저 노출되지 않도록 처리합니다.

코드 펜스, 인라인 코드, 들여쓴 코드, 수식·거듭제곱 연산자와 이스케이프된 별표는 보존합니다. 따라서 코드의 `2 ** 3`처럼 의미가 있는 문자열까지 일괄 삭제하는 처리는 하지 않습니다. 사용자 설명 및 검증용 인용 원문을 바꾸어 근거 검증을 통과시키지도 않습니다.

주요 파일: `src/lib/llm/prompts/output-rules.ts`, `src/lib/llm/transport.ts`, `src/lib/shared/plain-text.ts`, `src/lib/llm/live.ts`, `src/lib/llm/tutor.ts`, `src/lib/server/session-dto.ts`, 채팅·시험·오답·노트 표시 컴포넌트.

## 7. 시험 답안은 답만 작성

기존 답안 생성과 근거를 문장으로 바꾸는 처리에는 캐릭터 persona와 존댓말 대화 형식이 들어갔습니다. 시험 답안·채점 호출에서는 persona를 전달하지 않습니다. 모델은 사용자가 실제로 설명한 내용에서 근거 인용을 고르고, 서버가 원문 일치를 검증한 뒤 제한된 표시 변환으로 호칭·불필요한 대화 표현을 정리합니다.

서술형은 내용 중심 평서형으로, 객관식은 `3번` 같은 선택 번호만 표시합니다. 코드·수식·수치·부정·불확실성 및 근거 원문은 보존합니다. 배우지 않은 내용에 임의의 정답을 보충하지 않습니다. 저장된 답안의 근거 번호·수준·미학습 상태를 채점에 전달하여, 근거 없이 찍은 객관식 번호가 정답과 같더라도 기존 미학습 0점 규칙을 유지합니다.

주요 파일: `src/lib/llm/prompts/write-exam-answer.ts`, `src/lib/llm/prompts/grade-exam.ts`, `src/lib/shared/exam-answer-text.ts`, `src/lib/shared/exam-format.ts`, `src/lib/llm/live.ts`, `src/lib/llm/stub.ts`, `src/lib/llm/routes/handlers.ts`.

## 8. 핵심 학습 목표 5개와 시험 5문항 대응

기존 목표 스키마는 3개로 고정되어 있었고, `objectiveRefFor`는 문항을 `o1 → o2 → o3`으로 반복 배정했습니다. 시험 수만 달라져도 학습 범위는 세 목표에 머무를 수 있었습니다.

새 챕터 준비에서는 세 후배 모두 학습 목표 5개와 시험 5문항을 만듭니다. `o1 ↔ q1`부터 `o5 ↔ q5`까지 일대일로 대응하며, 목표와 문제 수·고유 ID·배점 합계·원문 근거를 검증합니다. 같은 개념의 문구만 바꿔 목표를 늘리지 않습니다. 학습에서는 해당 개념을 설명하도록 질문하고 시험에서는 그 개념을 정식 문제 형식으로 다시 평가합니다.

5개를 정하는 위치:

- `src/contracts/game.ts`: 새 챕터의 캐릭터별 `questionCount: 5`, 목표 참조의 일대일 대응.
- `src/lib/llm/prompts/prepare-session.ts`: 원문에서 서로 다른 핵심 개념과 각 시험 문제를 생성하는 지시.
- `src/lib/llm/schemas.ts`: 요청된 수의 고유 목표·문제·근거·형식 검증.
- `src/lib/llm/learning-plan.ts`: stub에서 원문에 근거한 별개 개념을 선정. 충분한 근거가 없으면 반복·가공 목표를 만들지 않고 실패를 알림.
- `src/lib/llm/live.ts`, `src/lib/llm/stub.ts`, `src/lib/llm/routes/handlers.ts`: 준비 결과 생성·검증·저장.
- `src/lib/llm/turn-state.ts`: 실제 준비된 목표에서 다음 학습 질문의 주제를 선택.

핵심 확인 질문은 서로 다른 준비 목표 5개를 각각 한 번 이상 다룹니다. 한 설명에 여러 개념이 함께 들어가면 학습된 내용은 모두 인정하되, 아직 확인 질문을 하지 않은 목표는 생략하지 않습니다. KU의 재확인이나 부족한 설명에 대한 질문이 추가될 수 있으므로 대화 메시지 수를 무조건 5회로 제한하지 않습니다. 졸업시험 10문항, 기존 연습 모드 3문항은 유지합니다.

**기존 데이터:** 이미 준비된 시험, 진행 중 답안, 결과·점수와 저장된 학습 목표는 유지합니다. 기존 시험을 삭제하거나 5문제로 재생성하지 않습니다. 신규 준비부터 5개 목표·5문항 구성이 적용됩니다.

원격 main 통합 전 자동 회귀 테스트는 총 168개 통과했습니다: LLM 105개, 서버 33개, 클라이언트 16개, 출력 표시·정규화 14개.

최종 production 빌드와 타입 검사를 통과했습니다. 전체 ESLint 오류는 0개이며, 기존 `src/app/layout.tsx`의 폰트 사용 경고 1개는 유지됩니다. 운영 모드에서도 서명 쿠키 인증, 세 후배의 저장된 5문항·100점 결과 조회, 서명 없는 쿠키 401, 체험 API 404, 결과 화면 표시를 확인했고 브라우저 예외는 0건입니다.

## 최신 main 통합

원격 `70bf5b7`의 정적 PNG 캐릭터·차량·배경, 모바일 홈 개선, 원격 libSQL/Turso 연결 지원을 함께 보존합니다. 동일한 버그를 수정한 두 버전은 새 세션 5개 목표·5문항, 검증된 USER 인용 기반 답안, 미학습 0점 판정과 원문·코드 보존 기준으로 통합했습니다. 유효한 쿠키의 계정 행이 사라진 경우에는 저장소 장애로 구분하며, 인증 요청에서 계정을 자동 재생성하지 않습니다.

추가로 확인한 `6a75877`의 컴돌이·컴순이 표시명, 홈·로그인·온보딩의 캐릭터 배치, 학습한 설명을 시험까지 보존하는 처리, 오답 원인 표시를 통합합니다. 객관식 답안 표시는 번호만 사용하고 근거는 별도 인용으로 유지합니다. 원격 변경에 포함된 졸업시험 5문항 설정은 이 대화에서 사용자가 명시한 10문항 기준으로 유지합니다. 이미 저장된 시험은 실제 문항 수를 표시합니다.

DB 시작 스크립트는 완전히 빈 저장소에만 시드를 적용합니다. 사용자 행이 0개라는 이유로 기존 저장소를 다시 시드하지 않으며, 기존 온보딩 완료 상태를 한 번만 보정합니다. 안전하게 추가할 수 없는 필수 컬럼이 있으면 시작 단계에서 별도 마이그레이션 필요를 알립니다. 실제 원격 DB 접속·운영 데이터 변경 없이 임시 SQLite로 해당 분기를 검증했습니다.

## 남은 확인 사항

- 운영 DB 영속 저장소 설정과 실제 장애 로그는 확인·변경하지 못했습니다. 유효 쿠키를 만료로 오인하는 코드와 화면 상태 초기화는 수정했지만, 이미 잃어버린 계정·학습 데이터를 복원한 것은 아닙니다.
- 이 클라우드에는 실제 Google OAuth/외부 LLM API 키가 없어 제공자와 연결한 전체 흐름은 검증하지 않았습니다. Google callback은 모킹된 제공자 응답으로, LLM 출력 경계는 주입한 모델 응답과 stub으로 검사했습니다.
- 이미 준비된 과거 시험의 문항 수와 학습 목표는 보존합니다. 신규 준비부터 5개 목표·5문항이 적용됩니다.
- 원문 근거가 부족한 자료에 임의의 목표를 덧붙이지 않습니다. stub에서 서로 다른 5개 개념이나 타당한 객관식 보기 4개를 만들 근거를 찾지 못하면 준비 실패로 알려 줍니다. 학습 대화의 선택지만 없는 경우에는 직접 설명할 수 있습니다. 실제 모델의 문항 품질은 실제 API 연결 후 별도 확인해야 합니다.
- DB와 검증용 인용은 원문을 유지합니다. 코드·수식 등 실제 필요한 별표는 강조 문법 제거 대상이 아닙니다.
